# AI Trip Generation

## Purpose

The AI feature creates a suggested trip plan from destination, duration, budget, and traveler preferences. The prompt and Gemini SDK integration are implemented in `src/constants/Options.jsx` and `src/service/AIModal.jsx`. The trip-creation screen composes the prompt and calls the exported chat session.

## Inputs

The form currently collects:
- destination (`location`);
- duration (`nOofdays`);
- budget tier (`budget`);
- traveler group (`traveler`).

The budget choices are Cheap, Moderate, and Expensive. Traveler groups include Just Me, A Couple, Family, and Friends. These are application-defined labels and not strict financial budgets or guaranteed accommodation classifications.

## Prompt composition

The `AI_PROMPT` constant contains placeholders for destination, total days, traveler group, and budget. The trip creation screen replaces those placeholders with form values. It asks the model to return a JSON object with trip details, hotel recommendations, and an itinerary grouped by day.

Prompt wording is not a schema guarantee. A generative model may produce malformed JSON, omit required properties, return additional prose, or use different field names.

## Model configuration

`src/service/AIModal.jsx` initializes the Google Generative AI SDK using `VITE_GOOGLE_GEMINI_AI_API_KEY`. The source configures a Gemini model and generation parameters, including temperature, top-p, top-k, maximum output tokens, and JSON response MIME type. It also starts a chat session seeded with an example conversation.

The configured model name and SDK support can change. Confirm current provider model availability and key requirements before deployment. The model is called from browser code, which exposes the configured key in the client build.

## Current response handling

The trip creation flow obtains response text and passes it to a save function. The save function attempts to parse the string using `JSON.parse`. It shows a toast when parsing fails and otherwise saves the parsed data to Firestore.

The current implementation does not fully validate the parsed object against a formal schema. A valid JSON object can still be incomplete, incorrectly typed, excessively large, or inconsistent with the view components' expectations.

## Expected response structure

The UI expects a top-level `hotel_options` array and an `itinerary` object. The itinerary should contain day entries with `best_time_to_visit` and a `places` array. Hotel components read fields including `HotelName`, `HotelAddress`, `Price`, and `Rating`. Place components read descriptive and display fields.

Use [Data Model](data-model.md) for the expected application-side shape.

## Validation recommendations

Before persisting generated data:
1. strip permitted formatting fences only if the model response contract allows them;
2. parse JSON inside an error boundary;
3. require a plain object at the top level;
4. check required fields and field types;
5. validate hotel and place arrays element by element;
6. bound text lengths and collection sizes;
7. validate URLs and coordinate formats;
8. reject invalid or empty itineraries;
9. handle unknown fields safely;
10. persist only the normalized validated object.

Prefer a runtime schema validator with a documented schema version. Do not render raw HTML generated by the model.

## Reliability and user experience

The UI should represent generation as an asynchronous operation. Add clear loading states, timeouts, retry controls, and errors for provider quota, network failure, unavailable model, invalid output, and Firestore save failure. Ensure loading state is reset in a `finally` block so unexpected exceptions do not leave the interface stuck.

Avoid duplicate submissions while a request is pending. Consider abort and cancellation behavior if the provider supports it.

## Accuracy and user safety

Generated destinations, hotels, prices, ratings, opening times, travel times, images, and geographic coordinates may be inaccurate or outdated. The model does not confirm availability or create bookings. Clearly label results as generated suggestions and ask users to verify information with official sources.

## Security and privacy

Do not log full prompts, profile information, access tokens, or complete itineraries in production. Move privileged model access behind a server-side endpoint. Apply quotas and abuse controls. Review user-entered text before including it in prompts.

See [API](api.md), [Security](security.md), [Privacy](privacy.md), and [Testing](testing.md).
